## Required behavior and change surface

1. Saved invoice.extract 1.0 selections remain 1.0 after decode, reopen and rediscovery. If only 2.0 is offered, new work visibly refuses before submission; no automatic rebinding, silent drop, new job, or retry loop. Preserve rule/job/request identities and immutable historical rule versions. Test unchanged and changed provider app/version/instance separately.
2. An accepted legacy job that returns failed/INTERRUPTED/nonretryable remains terminal, visible and attributable to its original admission. A new legacy POST refused with UNSUPPORTED_CAPABILITY/nonretryable also terminates visibly. Repeated queue pumps, application reopen and rediscovery cannot automatically resubmit either as 1.0 or 2.0. Uncertain acceptance retains the existing GET reconciliation policy; do not turn transport errors into proof of refusal.
3. Recovery is an explicit new selection and deliberate invocation of currently offered 2.0, with fresh request identity and existing confirmation/entitlement requirements. Old failed work is not restarted, relabelled or retroactively authorized. A saved-rule change uses the existing versioned rules put owner with expected-version conflict protection; it creates a new rule version for future work and never rewrites old fires. A stale confirmation must not authorize the replacement.
4. Completed 1.0 artifacts remain readable/exportable with identical bytes, sizes, hashes, capability/record identity and recorded context after reopening, provider disappearance and 2.0 rediscovery. No re-extraction, record conversion or new typed rendering. Preserve existing retention/purge and source-admission rules. Test retained results with the recorded context and reject a substituted 2.0 context.
5. Visible recovery copy must explain that the saved invoice selection is unavailable and a new selection is required, using existing structured error/reason signals. Do not parse error.message or infer a replacement version from free text. The canonical matcher remains the authority; the UI renders its outcome. No provider-specific version registry or parallel validator.

Expected minimal implementation owners: the existing discovery/dispatch/terminal owners in `engine_api.py`, snapshot/result owners in `connect_selection.py`/`db.py` only if a failing regression proves a defect, and existing inbox outcome/selection presentation in `desktop/src/main.ts`, `automationOutcome.ts`, `connectAvailability.ts` and their adjacent tests. Every source edit requires a reproduced failure, introducing commit and owner explanation first. If current behavior already meets an invariant, add the proof without rewriting it.

The missing general invoice-rule editor is an explicit limitation. This proposal permits proof of versioned rule reselection through the existing engine API and visible inbox guidance, plus deliberate generic inbox invocation; it does not claim a desktop invoice-rule editing flow exists. If operator-facing completion requires a new rule editor or CLI, revise this contract with that concrete product flow and obtain acceptance before building it. Do not route invoice work through the COI editor or silently widen its certificate filter.

## Verification plan and assertion map

- **Selection/decoder:** round-trip and fresh-process store reopen preserve the complete snapshot except intentionally excluded credentials. 1.0 against 2.0-only refuses before attachment handoff/POST; matching 2.0 explicitly selected succeeds. Missing, mixed, duplicate and unsupported identities retain existing structural admission. Controls change provider version/instance independently.
- **Transport/lifecycle:** use the existing real-HTTP reference provider for failed INTERRUPTED status and HTTP 400 UNSUPPORTED_CAPABILITY, both nonretryable. Assert original stored identity, visible terminal reason and no further POST after pump/reopen. Keep transient transport/retryable busy controls and uncertain-write reconciliation. Status failure and submission refusal are separately asserted.
- **Recovery/concurrency:** deliberate 2.0 selection uses a fresh request and normal confirmation. A concurrent rule update rejects stale expected_version; old fires and confirmations remain bound to their original version. Discovery changing between selection and invocation still refuses at the existing owner.
- **Replay:** compare whole output bytes/digests and complete recorded request/result context across reopen and 2.0 discovery. Present/export works without a current provider; invalid bytes/hash, wrong job identity and context substitution still refuse. No payload-derived financial claim is introduced.
- **UI:** test reason-aware text at its existing presentation owner and an isolated inbox render/action path. The refusal cannot be hidden by a catalog refresh or mislabeled as an active retry. A replacement invocation requires a user action. Saved-rule API proof is labelled API-only, not installed UI proof.
- **Origin discipline:** declare the expected fail-first case before running it, preserve original evidence, fix the first divergence and demonstrate regression failure when the fix is removed. Assertions above map to contract invariants, not implementation output. Use existing typed models/structured APIs; schema-expressible constraints stay with their schema owner.
- **Adjacent gates:** targeted Python and frontend tests, applicable lint/type/build checks, then required CI/native jobs. Do not duplicate broad CI locally unless the project gate requires it or CI is unavailable. Any installed guest replay needs its own exact-head review, package identity/parity and resource gates; no guest execution is authorized by this planning step.
