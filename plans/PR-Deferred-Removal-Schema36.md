## Additive shape

0. `message_removal_requests`: `request_id` primary key, constrained `kind`, `parameters_sha256`, and canonical UTC `accepted_at`. This request owner persists acceptance even with zero targets; no invented or empty mailbox binding. The fingerprint covers canonical kind and scope selection, and reusing the key with different parameters is rejected. It contains no content or credentials. Bound intents reference this owner by foreign key. Aggregate status and counts are always derived from its children (zero children means completed with zero counts), never stored twice. This remains an additive schema-36 migration, with no new version.
1. `message_removal_intents`: opaque `intent_id` primary key; a caller operation/idempotency key; frozen provider/account/mailbox binding; constrained kind (`delete`, `clear`, `unfollow`); canonical UTC acceptance time; constrained state (`pending`, `completed`); requested/completed logical-target counts; nullable canonical UTC settlement time. A clear spanning retained scopes creates bound sibling intents behind one persisted request key and one aggregate status; it does not give one intent authority over another mailbox. A retry reuses its request key and frozen selection rather than selecting later arrivals.
2. `message_removal_targets`: foreign key to its intent, stable logical-target identity and stable stored `message_id` text identity, frozen effective source binding and source identifiers needed for completion, constrained target state, and settlement time. Capture the whole selected logical unit through `_logical_unit` and its existing effective-identity/source membership helpers; never persist SQLite rowid or introduce a second message-key algorithm. All members of a unit share its logical-target identity; counts are logical targets, not alias rows. An unfollow target denotes content cleanup and never hides message headers.
3. Uniqueness: intent IDs are globally unique; the operation key plus its frozen binding is unique (separate NULL/non-NULL identity indexes preserve uniqueness for unresolved legacy identities). Target membership is unique per intent/stable message identity. Add indexes for active target lookup by stable message identity and binding, logical-unit target grouping, and pending intent resumption.
4. Targets reference intents with `ON DELETE CASCADE`. Do not make a physical message/account deletion silently erase its durable completion identity: target bindings are immutable metadata, not a cascading FK to live message/account rows. A missing bound target is completed through the same completion owner; a reused message ID in another binding cannot be deleted or hidden by the old intent.
5. Retain settled status/counts as non-content operational receipts until the existing retention maintenance owner retires the request group after every child has settled and passed the existing retention interval; never retire a pending sibling or use capture-suppression expiry to retire its barrier. Retirement removes the request, its intents and target metadata together, so aggregates do not lose settled siblings. An expired, retired request key is rejected without selection or deletion; it never silently becomes a fresh clear. A deliberate new operation gets a new key. The key issuer/parser and receipt retirement must enforce this after a restart or retention-setting change; exact key-expiry mechanics require oversight readthrough before implementation. No content or provider credentials belong in these tables. Account/profile-removal behavior remains outside this slice and #259 is untouched.

No messages-table rebuild, row renaming, body rewrite or migration-time deletion. Legacy NULL identity uses the existing effective-identity/continuity owner; do not invent a mailbox identity during migration or acceptance.

### Runtime assertion interface clarification

Oversight answer `44e79cf0` to `fcfe13cb` clarifies the existing runtime ownership requirement without changing behavior. One private lexical scope acquires the native operation lock and then the acceptance protocol guard before yielding its capability. API delete/clear and `_with_watchlist_mutation` replace their existing operation-lock scope with this owner; they do not acquire an operation lock separately and then mint authority. Direct `Store.request_removal`/acceptance callers must pass the required capability, and Store acceptance never acquires a lock internally. Missing/None authority refuses before writes.

The capability is constructible only by its acquiring scope, bound to process, thread and canonical database path, passed only through the call chain, and invalidated on scope exit. The acceptance helper requires a connection/write transaction opened after that acquisition inside the same scope; passing an earlier connection/transaction is refused. Runtime and migration authority are distinct types, and neither entry accepts the other kind. This is explicit ownership proof, with no registry, thread-local/global guard state, reentrancy or reuse mechanism. Physical completion takes no acceptance capability; `selected_source_locks` and its existing guard lifetimes stay unchanged.

Required runtime controls are forged, stale, cross-thread and wrong-connection refusal; transaction-before-guard refusal; missing/None capability refusal before writes; and the real API path completing under a bounded harness without a second native operation-lock acquisition. The earlier derived-writer/source-context audit and migration proof list still apply.

### Lexical operation owner and acceptance segments

The existing top-level native operation acquisition mints one private operation owner, bound to process, thread and canonical database path and invalidated on release. The owner is passed explicitly through the call chain; it is not a reentrancy token. Each segment commits, invalidates its capability and releases its guard before physical work. Public `acceptance_scope` composes this same operation owner with one segment. ### Accepted lost Clear lifecycle

Operator decision, relayed verbatim in [issuecomment-6220700441](https://github.com/canfieldjuan/eom-email-watcher/pull/261#issuecomment-6220700441): **"Tell me, don't redo (Recommended)"**. The accepted option says: "Show a plain note: 'Your last Clear didn't go through; nothing was deleted.' The normal Clear button stays; clicking it is a fresh Clear of what's there now. A Clear that DID go through just shows its pending/done status — never sent twice."

The client durably saves only the opaque signed key plus kind and parameters before its mutation RPC. After a lost reply or restart it reads status for that saved key; it never submits that request again. A found receipt shows its deferred/completed status and counts. A valid unknown key returning `not_found` shows exactly "Your last Clear didn't go through; nothing was deleted.", discards that key, and leaves the normal Clear button. Malformed/forged/expired-key errors retain the existing backend error semantics; `not_found` is not inferred from another error.

Every later explicit Clear click is a new request with a new key and a new frozen selection. Earlier pending receipts remain separate and are shown separately. There is no automatic resend or retry button. Counts and message content are never copied into the saved-key journal.

Required controls: a lost reply after commit followed by restart reads status with zero resubmits; a lost reply before commit shows the approved note, and a later explicit Clear uses a new key; another Clear while an earlier receipt is pending keeps both receipts and selects later arrivals correctly. This records the accepted policy before the desktop action implementation; it is not proof that the UI is wired or durably persists keys yet.

### Initialization and admitted completion

The startup notification worker has an existing 30-second operation deadline
(`desktop/src-tauri/src/lib.rs`, `STARTUP_DELIVERY_TIMEOUT`). It includes the
`host.operation_lock` RPC, which loads a runtime before returning the lock path.
Physical removal can consume the existing 90-second source wait. Running it on
every runtime open therefore makes even that lock-location request time out
while a pending target's source is held. This came from the completion added to
`source_locks.qualify_protocol` in `043ee944` and reached by `Store.initialize`.

`Store.initialize` establishes the source protocol through the shared
`source_locks.initialize_protocol` owner without running physical completion.
The explicit `qualify_protocol` entry consumes that same protocol setup and
retains its operation-owned completion and source-context refusal. Ordinary
checks and accepted removals keep their existing completion entries. There is
one physical removal implementation, `removal.resume`; its source wait, lock
order and frozen targets stay unchanged. No host-RPC exemption, cached lock
path, timeout increase or new retry is introduced.

Required proof: opening a pending store qualifies it without calling completion
or changing its retained bytes; explicit qualification then settles that same
receipt. Restoring completion on initialization must fail the regression. The
real native startup notification probe retains the production startup budget
and uses a real source holder, covering selection before acceptance, selection
after acceptance, and acceptance excluded through platform send and ack.
